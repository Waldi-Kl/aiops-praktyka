k8sgpt: reguły wykrywają, AI tłumaczy

Wykrywanie problemów to deterministyczne reguły uruchamiane lokalnie. LLM pojawia się dopiero z flagą --explain: dostaje gotowy tekst błędu i odsyła krótkie wyjaśnienie. Tylko wtedy dane wychodzą poza laptop i klaster.

Jak przepływa jedno k8sgpt analyze --explain (nasze szkolenie)

  1. Odczyt stanu. CLI czyta zasoby z API serwera Twoim kubeconfigiem, jak kubectl get. Uprawnienia k8sgpt = Twoje uprawnienia.
  2. Reguły. Analyzery w Go sprawdzają status i konfigurację obiektów i budują listę problemów. Zawsze ten sam wynik, bez AI, nic nie wychodzi na zewnątrz.
  3. Zapytanie do modelu (--explain). Jedno zapytanie na każde znalezisko: tekst błędu w szablonie promptu. Model nie czyta logów i niczego nie dopytuje. Bez --namespace na naszym EKS to 22 zapytania, z czego 21 o szum.
  4. Brama. LiteLLM sprawdza klucz wirtualny i budżet, tłumaczy zapytanie na API Anthropic i wycina parametry, których model nie przyjmuje.
  5. Odpowiedź. Krótkie wyjaśnienie i sugestia (do ok. 280 znaków) wraca do terminala i trafia do lokalnego cache, więc ten sam błąd nie pójdzie drugi raz do modelu (--no-cache to wyłącza).

Trzy tryby pracy: kto uruchamia analizę i dokąd trafia wynik

Co z tego wynika

Zielony wynik ≠ działa

k8sgpt widzi stan obiektów, nie metryki ani logi. Błędy 500 przy zielonych podach, wysokie CPU czy pojedynczy OOMKill przejdą niezauważone.

Zawężaj przed --explain

Każde znalezisko to płatne wywołanie modelu. Na naszym EKS skan całości: 22 znaleziska, 1 prawdziwe.

Model to konfiguracja

k8sgpt nie ma własnego modelu. LiteLLM, Anthropic wprost albo Ollama lokalnie to tylko inny wpis w k8sgpt auth.

To nie agent

Jedno zapytanie, jedna odpowiedź, bez pętli. Agentem jest HolmesGPT albo asystent korzystający z k8sgpt przez MCP.
