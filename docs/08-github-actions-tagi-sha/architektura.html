Tag czy SHA: skąd pipeline bierze cudzy kod

Każda linijka uses: to cudzy kod pobierany przy każdym przebiegu i uruchamiany w jobie z Waszymi sekretami. Tag mówi „daj to, co dziś nazywa się v5”. SHA mówi „daj dokładnie ten kod, który sprawdziłem”.

1. Co się dzieje przy starcie joba

  1. Workflow wskazuje akcję. actions/checkout@v5 = repo actions/checkout, ref v5. Checkout klonuje Wasze repo na runner, żeby kolejne kroki miały na czym pracować.
  2. Runner pyta o tag. Przy każdym przebiegu sprawdza, na jaki commit wskazuje dziś v5. Tag to tylko wskaźnik — może wskazywać dziś na co innego niż wczoraj.
  3. Pobiera kod z tego commita. W logu joba (Set up job) widać, który SHA faktycznie pobrał.
  4. Uruchamia go w Waszym jobie. Akcja nie jest w piaskownicy: widzi sekrety joba, GITHUB_TOKEN, poświadczenia chmury i pliki repo.

2. Atak: przestawiony tag kontra przypięty SHA

  1. Przestawienie tagu. Napastnik z prawem push (token bota, przejęte konto, niedokończona rotacja kluczy) dodaje commit X i przestawia na niego tagi. Dwie komendy, bez śladu w historii, który zobaczyłby użytkownik.
  2. Pipeline sam pobiera X. Przy najbliższym przebiegu runner pyta „na co wskazuje v5?” i dostaje X.
  3. Wyciek i zielony build. X czyta sekrety z env i pamięci runnera, wysyła je na zewnątrz, potem robi normalną pracę. Nikt nie zauważa.

3. Warstwy obrony

Przypnij do SHA

@<40 znaków> # v5.0.1. Hash z git ls-remote, nie z pamięci ani z modelu.

Aktualizuj przez PR

Dependabot github-actions: nowy SHA z changelogiem przechodzi review.

Ogranicz szkody

permissions: per job, OIDC zamiast kluczy, sekrety tylko tam, gdzie trzeba, persist-credentials: false.

Sprawdzaj narzędziem

zizmor: unpinned-uses, excessive-permissions, artipacked. actionlint: składnia.

Wymuś w organizacji

Polityka allowed actions z wymogiem SHA (od 08.2025). Autorzy akcji: immutable releases (od 10.2025).
