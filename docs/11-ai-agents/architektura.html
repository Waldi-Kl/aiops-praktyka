Agent AI: model prosi, nasz kod wykonuje

Agent to model wywołujący narzędzia w pętli. Model niczego nie uruchamia: zwraca JSON z nazwą narzędzia i argumentami. Wykonuje to nasz kod, więc to my decydujemy, jakie narzędzia agent ma, z jakimi uprawnieniami i ile kroków może zrobić.

Jak działa pętla agenta (przykład agent_raw.py z Responses API)

  1. Zadanie. Człowiek, alert albo pipeline daje zadanie. Trafia do listy history, czyli pamięci krótkotrwałej agenta.
  2. Zapytanie do modelu. Kod wysyła responses.create: instrukcje, całą history i opisy narzędzi w JSON Schema. Historia rośnie z każdym krokiem, więc rośnie koszt tokenów.
  3. Prośba o narzędzie. Model zwraca function_call, np. get_pod_logs(namespace="shop", pod="cart"). To tylko JSON. Model sam wybiera kolejność narzędzi, ale żadnego nie uruchamia.
  4. Wykonanie przez nasz kod. Kod wywołuje wąską funkcję z listy dozwolonych (AVAILABLE[call.name]), która uruchamia kubectl bez powłoki. Wynik idzie do history jako function_call_output i pętla wraca do kroku 2. Log z wyniku to niezaufana treść: może zawierać prompt injection.
  5. Akcja zapisu tylko po zgodzie. Narzędzie zapisujące, np. restart_deployment, zatrzymuje pętlę i czeka na człowieka (approve / reject / edit). W LangChain robi to middleware HITL z checkpointerem, w Agents SDK zatwierdzanie wywołań narzędzi.
  6. Koniec. Gdy model nie prosi już o narzędzie, jego tekst jest odpowiedzią końcową. Limit kroków (range(10), max_turns, recursion_limit) przerywa pętlę, zanim zje budżet.

Co z tego wynika

Model nic nie wykonuje

Zwraca JSON. Uprawnienia agenta to dokładnie te narzędzia i ta tożsamość, które dał mu nasz kod.

Wąskie narzędzia

get_pod_logs(ns, pod) zamiast run_shell(cmd). Odczyt domyślnie, zapis tylko przez zgodę człowieka.

Każdy krok kosztuje więcej

Cała historia idzie do modelu przy każdym kroku. Limit kroków i budżetu to obowiązek, nie opcja.
